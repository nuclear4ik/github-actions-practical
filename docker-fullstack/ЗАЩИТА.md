# Защита практической по Docker

Это шпаргалка по нашему проекту `docker-fullstack`. Читать сверху вниз: сначала речь, потом цикл, потом `docker-compose.yml`, в конце 20 вопросов по коду.

На защите обычно 5 минут показа и около 10 минут вопросов. Показывать надо живой стек, а не пересказывать файл.

## Что открыть и что сказать в начале

Каталог: `docker-fullstack`.

Команды, которые стоит показать по порядку:

```bash
cd docker-fullstack
docker compose ps
curl -s http://localhost:8080/api/items
docker compose logs app
docker images app-backend:1.0.0
```

В браузере открыть http://localhost:8080. На странице должны быть две строки: `1. first item` и `2. second item`.

Если контейнеры уже остановлены:

```bash
docker compose up -d --build
```

Остановить после защиты:

```bash
docker compose down
```

`down` удаляет контейнеры и сеть. Том `db_data` с данными базы остаётся. Чтобы стереть и базу тоже: `docker compose down -v`.

## Текст для защиты

Можно почти дословно.

Мы собрали fullstack: Go-сервер, статическая страница и PostgreSQL. Образ приложения собирается в два этапа. Первый этап — `golang:1.22-alpine`, там компилятор. Сначала копируются `go.mod` и `go.sum`, выполняется `go mod download`, и только потом исходники. Поэтому при правке кода зависимости берутся из кэша. Процесс идёт от пользователя 65532, shell в образе нет.

## Полный цикл: что происходит от команды до страницы

1. `docker compose up -d --build` читает `docker-compose.yml` и файл `.env` рядом с ним. Подставляет переменные: `${DB_USER:-app}` берёт значение из `.env`, а если его нет — пишет `app`.
2. Compose создаёт сеть `app_net` и том `db_data`, если их ещё нет.
3. Собирает образ `app`. Клиент отправляет демону каталог `backend` — это контекст сборки. `.dockerignore` выкидывает из него лишнее.
4. Этап `builder`: базовый образ Go, рабочая папка `/build`, копирование `go.mod` и `go.sum`, `go mod download`, копирование кода, сборка `/out/app`.
5. Этап `nonroot`: из builder копируется только бинарник в `/app/app`. Компилятор остаётся в промежуточном этапе и в итоговый образ не входит.
6. Образ получает имя `app-backend:1.0.0`.
7. Стартует контейнер `app-db` из `postgres:16-alpine`. Порт 5432 слушается внутри контейнера, на Мак он не проброшен.
8. Если том `db_data` пустой, Postgres сам создаёт пользователя, пароль и базу из `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`. Потом выполняет скрипты из `/docker-entrypoint-initdb.d`. Туда смонтирован наш `init/01_seed.sql`.
9. Каждые 5 секунд healthcheck запускает `pg_isready`. Пока проверка не успешна, сервис `db` не считается healthy.
10. Только после этого стартует контейнер `app`. Ему проброшен порт `8080:8080`, в окружение переданы `DB_HOST=db` и остальные переменные, каталог `frontend` примонтирован в `/app/static` только на чтение.
11. Программа читает переменные, открывает описание подключения к Postgres и слушает `:8080`. Само соединение с базой в этот момент ещё не обязательно установлено: `sql.Open` только готовит пул.
12. Браузер открывает `localhost:8080`. Docker на Маке принимает соединение на порту хоста 8080 и передаёт его в порт 8080 контейнера.
13. Go отдаёт `index.html` из `/app/static`. Страница скриптом запрашивает `/api/items`.
14. Обработчик делает `SELECT id, name FROM items`. Запрос идёт на хост `db`. Встроенный DNS Docker превращает имя `db` в IP контейнера базы в сети `app_net`.
15. Ответ `[{"id":1,"name":"first item"},{"id":2,"name":"second item"}]` страница рисует списком.

Образ и контейнер — разные вещи. Образ собран и неизменяем. Контейнер — запущенная копия. Слои образа только для чтения. Запись контейнера лежит в отдельном тонком слое сверху и пропадает вместе с контейнером, если данные не лежат в томе.

## `docker-compose.yml`: что за что отвечает

Файл описывает стек. Compose его не «запускает как программу», а создаёт по нему сеть, тома и контейнеры.

### `services`

Список контейнеров этого проекта. У нас два: `app` и `db`. Имя сервиса — это DNS-имя внутри сети. Поэтому в коде база называется `db`.

Если переименовать сервис `db` в `postgres` и забыть поменять `DB_HOST`, приложение будет искать хост `db` и получит ошибку резолва. Запрос `/api/items` вернёт 500.

### `app.build.context: ./backend`

Какой каталог отправить демону на сборку. `COPY` в Dockerfile видит только файлы отсюда.

Если указать `./` или домашний каталог, в контекст попадёт лишнее, сборка станет тяжелее, а `COPY go.mod` может не найти файл, потому что он лежит в `backend`, а не в корне. Если указать несуществующий путь, сборка упадёт сразу.

### `app.build.dockerfile: Dockerfile`

Имя рецепта внутри контекста.

Если переименовать файл и не поменять эту строку, Compose напишет, что Dockerfile не найден.

### `app.image: app-backend:1.0.0`

Имя и тег готового образа. `build` говорит, как собрать, `image` — как назвать. Тег `1.0.0` фиксирует версию. `latest` так не делает: под одним именем может оказаться разная сборка.

Если поменять тег на `1.0.1`, новая сборка получит новое имя. Старый контейнер останется на старом образе, пока его не пересоздать через `up --build` или `up --force-recreate`.

### `container_name: app` и `container_name: app-db`

Фиксированное имя контейнера, его видно в `docker ps`.

Если имя уже занято другим контейнером, новый не стартанёт. Если строку убрать, Docker сам даст имя вида `docker-fullstack-app-1`. Для этой лабораторной фиксированное имя удобно. В проде с несколькими копиями одного сервиса его обычно не ставят.

### `ports: "8080:8080"`

Левое число — порт на Маке, правое — порт внутри контейнера. Браузер ходит на левое.

Если поставить `"9090:8080"`, сайт откроется на http://localhost:9090, а внутри приложение по-прежнему слушает 8080. Если поставить `"8080:9090"` и не поменять `HTTP_PORT`, на хосте порт откроется, но внутри на 9090 никто не слушает: соединение оборвётся. Если убрать `ports` совсем, контейнер будет слушать 8080 только внутри сети Docker, с Мака страница не откроется. Если 8080 на Маке уже занят, контейнер не стартанёт.

`EXPOSE 8080` в Dockerfile порт наружу не открывает. Его открывает именно `ports` или флаг `-p`.

### `environment`

Переменные внутри контейнера. Код читает их функцией `env` в `main.go`.

| Переменная | Зачем | Если поменять |
|---|---|---|
| `HTTP_PORT` | Порт, который слушает Go | Должен совпасть с правым числом в `ports`. Иначе проброс смотрит не туда |
| `STATIC_DIR` | Папка со страницей | Если указать другой путь, а том монтируется в `/app/static`, страница будет 404 |
| `DB_HOST` | Имя базы в сети | `localhost` здесь — сам контейнер приложения, Postgres там нет. Нужно имя сервиса `db` |
| `DB_PORT` | Порт Postgres | Должен остаться 5432, пока у базы стандартный порт |
| `DB_USER`, `DB_PASSWORD`, `DB_NAME` | Логин в базу | Берутся из `.env`. На уже созданном томе пользователь Postgres не пересоздаётся |

`${DB_USER:-app}` значит: взять `DB_USER` из окружения или из `.env`, а если пусто — подставить `app`. То же для пароля и имени базы.

Если удалить `.env`, подставятся значения после `:-`: пользователь `app`, пароль `secret`, база `appdb`. Они должны совпасть у `app` и у `db`. Если пароль приложению передать один, а Postgres при первом создании получил другой, `/api/items` упадёт с ошибкой аутентификации.

### `volumes: ./frontend:/app/static:ro`

Слева путь на Маке, справа путь в контейнере, `:ro` — только чтение.

Страница не запечена в образ. Go читает файлы с диска. Поэтому правку `index.html` видно после обновления браузера, без пересборки образа.

Если убрать `:ro`, процесс в контейнере сможет менять файлы на Маке. Если убрать всю строку, в `/app/static` пусто, главная страница не найдётся. Если смонтировать не ту папку, отдадутся чужие файлы.

### `depends_on` и `condition: service_healthy`

Порядок старта. Просто `depends_on: db` ждёт, пока контейнер базы создан и процесс запущен. База в этот момент может ещё инициализироваться.

`condition: service_healthy` ждёт зелёный healthcheck. Поэтому `app` не стартует раньше Postgres.

Если оставить только `depends_on` без `condition`, наш процесс всё равно поднимется: `sql.Open` не ходит в сеть сразу. Упадёт первый `SELECT`, страница покажет ошибку API, пока база не будет готова. Если убрать `depends_on` совсем, гонка та же, только ещё и без порядка запуска.

### `restart: unless-stopped`

Контейнер поднимется снова, если сам упал, если перезапустился Docker или Мак. После явного `docker compose down` сам не поднимется.

`always` поднимает даже после ручной остановки, когда демон Docker стартует снова. `no` или отсутствие поля — после падения контейнер останется выключенным. `on-failure` поднимает только если процесс завершился с ненулевым кодом.

### `networks: app_net`

Оба сервиса в одной сети и видят друг друга по имени.

Если поставить приложению другую сеть и не добавить туда базу, имя `db` не зарезолвится. `driver: bridge` — обычная виртуальная сеть Docker. На Маке сеть `host` не работает как на Linux, её в этой работе не используют.

### `db.image: postgres:16-alpine`

Готовый образ, свой Dockerfile для базы не нужен. Тег `16-alpine` — 16-я ветка Postgres на Alpine, это не плавающий `latest`.

Если сменить мажорную версию, например на `postgres:17`, старый том от 16 может не запуститься: формат данных другой. Тогда нужен новый том или `docker compose down -v`.

### `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`

Их читает официальный entrypoint Postgres только когда каталог данных пустой.

Если поменять пароль в `.env` после первого успешного запуска, в томе уже лежит старый кластер. Новый пароль контейнер проигнорирует, приложение перестанет входить. Чтобы применить нового пользователя, надо удалить том: `docker compose down -v`, затем снова `up`. Данные при этом сотрутся, и `01_seed.sql` выполнится заново.

### `healthcheck`

`test` запускает `pg_isready` с тем же пользователем и базой. `interval: 5s` — пауза между попытками. `timeout: 3s` — сколько ждать одну попытку. `retries: 10` — сколько неудач подряд допустимо. `start_period: 10s` — стартовые неудачи в этот период не копят счётчик так же жёстко, базе дают время на initdb.

Если ошибиться в пользователе внутри `pg_isready`, проверка никогда не станет зелёной. Compose будет писать `app-db Waiting`, а `app` не запустится. Если сделать `retries: 1` и короткий `start_period`, медленный первый запуск можно не дождаться.

### `db_data:/var/lib/postgresql/data`

Именованный том Docker. Файлы базы живут в нём, а не в тонком слое контейнера. `docker compose down` том не удаляет, `down -v` удаляет.

Если убрать этот том, данные останутся только в контейнере и пропадут при его удалении. Следующий `up` снова выполнит init и снова вставит две строки.

### `./init:/docker-entrypoint-initdb.d:ro`

Скрипты первого запуска. Postgres выполняет их один раз, когда данные ещё пустые, по алфавиту имени файла.

Если дописать в SQL третью строку и просто перезапустить контейнер, ничего не изменится: каталог данных уже не пустой. Скрипт отработает снова только после `docker compose down -v`. Если в SQL будет ошибка на самом первом старте, инициализация базы оборвётся и healthcheck не позеленеет.

### Почему у `db` нет `ports`

База должна быть доступна приложению и недоступна с Мака. Сейчас в `docker compose ps` у неё `5432/tcp` без `0.0.0.0`.

Если добавить `"5432:5432"`, к Postgres сможет подключиться любой процесс на компьютере, а при занятом порте 5432 контейнер не стартанёт.

## Что отвечать про Dockerfile

Два `FROM` — два этапа. Имя первого этапа `builder` нужно для `COPY --from=builder`.

Порядок `COPY go.mod` → `RUN go mod download` → `COPY . .` — из лекции про кэш. Docker сравнивает инструкцию и файлы этого шага. Пока `go.mod` и `go.sum` те же, шаг `go mod download` помечается `CACHED`. Если поменять инструкции местами и сначала копировать весь код, любая правка `.go` сломает кэш и модули скачаются заново.

`CGO_ENABLED=0` собирает бинарник без сишных библиотек. `distroless/static` не содержит glibc, обычная динамическая сборка там не запустится.

`-ldflags="-s -w"` выкидывает таблицу символов и отладочную информацию. Файл меньше. Отладчик по нему почти слепой, для этой работы это нормально.

`USER` в файле нет: пользователь уже задан базовым образом `nonroot`. `docker inspect` показывает `User=65532`.

`EXPOSE` — пометка в метаданных образа. Без `ports` в Compose сайт снаружи не откроется.

`ENTRYPOINT ["/app/app"]` всегда запускает этот файл. Если бы стоял `CMD`, его проще полностью подменить другой командой при `docker run`. Аргументы по умолчанию как раз кладут в `CMD`.

## Что отвечать про `main.go`

`env` читает переменную окружения и, если она пустая, возвращает значение по умолчанию. Поэтому те же имена можно задать и из Compose, и руками через `docker run -e`.

`sql.Open` не подключается к базе сразу и не проверяет пароль. Ошибка соединения всплывает на `Query` в `/api/items`. Поэтому ранний старт приложения не роняет процесс, а ломает только запрос. Healthcheck как раз нужен, чтобы к моменту старта запрос уже мог пройти.

`_ "github.com/lib/pq"` — драйвер регистрирует себя в `database/sql` через `init`. Подчёркивание значит: пакет нужен ради этого побочного эффекта, напрямую его функции не вызываются. Без этой строки `sql.Open("postgres", ...)` не найдёт драйвер.

`/api/items` зарегистрирован отдельно от `/`. Более точный путь забирает запросы к API. Всё остальное отдаёт `FileServer` из `STATIC_DIR`. Для адреса `/` FileServer сам открывает `index.html`. Подменять путь на `/index.html` нельзя: сервер файлов в Go специально редиректит такой адрес обратно на каталог, получается петля.

`app.js` делает `fetch("/api/items")` на тот же хост и порт. Отдельный адрес фронтенда не нужен.

## 20 вопросов по коду

Отвечать своими словами, по 2–4 предложения. Ниже готовые формулировки.

**1. Зачем в Dockerfile два `FROM`?**  
Первый этап собирает программу и содержит компилятор. Второй этап — пустой runtime. Строка `COPY --from=builder /out/app /app/app` переносит только бинарник. Компилятор в итоговый образ не входит, поэтому он 13,9 МБ, а не сотни.

**2. Почему `COPY go.mod go.sum` стоит выше `COPY . .`?**  
Каждый шаг — слой. Пока не меняются файлы зависимостей, Docker берёт слой `go mod download` из кэша. Код копируется следующим шагом, и правка `main.go` пересобирает только компиляцию.

**3. Что будет, если сначала скопировать весь каталог, а потом сделать `go mod download`?**  
Любое изменение `.go` изменит слой с исходниками. Следующая команда скачает модули заново, хотя `go.mod` тот же. Сборка станет дольше, результат программы тот же.

**4. Что делает `CGO_ENABLED=0`?**  
Выключает cgo. Получается статически собранный бинарник без зависимости от glibc. В `distroless/static` этой библиотеки нет, с включённым cgo процесс бы не стартовал.

**5. Зачем `-ldflags="-s -w"`?**  
Флаги линковщика убирают символы и отладочную информацию. Бинарник меньше. На логику сервера это не влияет.

**6. Почему финальный образ `distroless ... nonroot`, а не `golang:1.22-alpine`?**  
Образ с Go тащит компилятор и shell. Distroless оставляет библиотеки и наш файл. Вариант `nonroot` сразу запускает процесс как пользователь 65532. В образе нет `/bin/sh`, это видно по ошибке `stat /bin/sh: no such file or directory`.

**7. `EXPOSE 8080` открывает порт на компьютере?**  
Нет. Это описание, какой порт слушает программа. Наружу его публикует `ports` в Compose. У базы `EXPOSE` из образа Postgres есть, но своего `ports` мы не писали, поэтому с Мака к 5432 не подключиться.

**8. Почему `ENTRYPOINT`, а не только `CMD`?**  
`ENTRYPOINT` закрепляет исполняемый файл `/app/app`. `CMD` обычно задаёт аргументы, и его легко заменить при запуске. Нам аргументы не нужны, порт и база приходят из переменных окружения.

**9. Что будет, если в `image` поставить `app-backend:latest`?**  
Сборка по-прежнему получится. По тегу нельзя понять, какая именно версия запущена: следующая сборка перезапишет то же имя. Поэтому стоит `1.0.0`.

**10. Что такое контекст сборки и зачем `backend/.dockerignore`?**  
`context: ./backend` — каталог, который клиент архивом отдаёт демону. `COPY` берёт файлы только из него. `.dockerignore` не даёт отправить в этот архив лишнее, например `.git`. Сборку из домашней папки запускать не нужно: контекст станет огромным.

**11. Как читать `"8080:8080"`?**  
Слева порт хоста, справа порт контейнера. Браузер открывает левый. Правый должен совпадать с `HTTP_PORT`, потому что Go слушает именно его: `addr := ":" + env("HTTP_PORT", "8080")`.

**12. Почему `DB_HOST` равен `db`, а не `localhost`?**  
`localhost` внутри контейнера `app` — это сам контейнер приложения. Postgres работает в другом контейнере. Имя сервиса `db` резолвится DNS-ом сети `app_net` в IP базы.

**13. Что означает `${DB_PASSWORD:-secret}`?**  
Compose подставляет переменную `DB_PASSWORD` из `.env`. Если её нет, подставит `secret`. Двоеточие с минусом — это значение по умолчанию. У приложения и у `POSTGRES_PASSWORD` выражение одно и то же, поэтому пароли совпадают.

**14. Зачем у тома фронтенда `:ro`?**  
Каталог Мака монтируется в `/app/static` только для чтения. Сервер может отдать `index.html`, `app.js` и `style.css` и не может их перезаписать. Если убрать монтирование, статики в образе нет и главная страница не откроется.

**15. Чем `depends_on` отличается от `condition: service_healthy`?**  
`depends_on` без условия ждёт старт контейнера. `service_healthy` ждёт успешный `pg_isready`. Инициализация Postgres занимает время, одного порядка запуска мало.

**16. Что будет, если удалить `healthcheck` у базы?**  
`condition: service_healthy` станет невозможен: Compose не знает, когда база готова, и `up` завершится ошибкой конфигурации. Если убрать и healthcheck, и condition, стек поднимется, но первый запрос к `/api/items` может получить ошибку соединения.

**17. Почему у сервиса `db` нет секции `ports`?**  
Порт 5432 слушается внутри сети `app_net`. Приложению этого достаточно, потому что оно ходит на `db:5432`. Снаружи порт не опубликован. Если добавить проброс, база станет доступна на Маке.

**18. Чем `db_data` отличается от `./frontend:/app/static`?**  
`db_data` — том, которым управляет Docker. В нём файлы Postgres, они переживают пересоздание контейнера. Вторая запись — bind mount: напрямую папка проекта. Её содержимое — обычные файлы на Маке, правка видна контейнеру сразу.

**19. Когда выполняется `01_seed.sql` и почему повторный запуск не добавляет ещё две строки?**  
Entrypoint Postgres запускает скрипты из `/docker-entrypoint-initdb.d` только если каталог данных пустой. После первого старта там уже есть кластер, скрипт пропускается. Чтобы выполнить его снова, нужен `docker compose down -v`: том удалится, инициализация пройдёт заново.

**20. Зачем в `main.go` пустой импорт `_ "github.com/lib/pq"` и почему `sql.Open` не падает, если база ещё спит?**  
Драйвер в `init` регистрирует имя `"postgres"` для пакета `database/sql`. Подчёркивание оставляет импорт, хотя в коде нет прямого вызова `pq`. `sql.Open` только создаёт объект подключения и проверяет, что драйвер известен. Сеть и пароль проверяются позже, на `db.Query` внутри `/api/items`. Поэтому рано запущенный процесс пишет `listening on :8080`, а ошибка базы появляется в ответе API.

## Если попросят сломать и починить

Это хорошие демонстрации, делать их лучше уже после основного показа.

- Поменять в `.env` только пароль и перезапустить без удаления тома. База останется со старым паролем, API начнёт отвечать ошибкой входа. Починка: вернуть прежний пароль либо `docker compose down -v` и поднять заново.
- Поставить `DB_HOST: localhost`. Страница контейнера откроется, `/api/items` вернёт 500, потому что Postgres не внутри контейнера `app`.
- Убрать монтирование `./frontend`. Образ перезапускать не обязательно, достаточно пересоздать контейнер. Главная станет 404, сам бинарник при этом жив.
- Показать кэш: поменять комментарий в `main.go`, снова `docker compose build`. `go mod download` будет `CACHED`, шаг `go build` выполнится заново.
